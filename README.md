# Рефакторинг OrderService

В ходе работы я разбил монолитный метод `processOrder` на отдельные классы и применил паттерны **Strategy** и **Factory Method**.

## Применение принципов SOLID

1. **SRP (Единственная ответственность).** В легаси-коде `OrderService` сам считал скидки, комиссии, печатал чек и сохранял заказ. Теперь он только управляет процессом. За расчеты отвечают классы стратегий (`DiscountStrategy`, `CommissionStrategy`), а за печать чека — `ReceiptPrinter`.
2. **OCP (Открытость/Закрытость).** Раньше, чтобы добавить новый тип клиента, нужно было лезть в метод и дописывать `else if`. Теперь достаточно создать новый класс скидки и добавить одну строку в `DiscountFactory`. Сам `OrderService` при этом не меняется.
3. **LSP (Подстановка Лисков).** Вместо сравнения строк (`"VIP"`, `"CARD"`) теперь используются объекты, реализующие общий интерфейс. Любую стратегию можно подставить в сервис, и он отработает корректно.
4. **ISP (Разделение интерфейсов).** Я разделил логику на два независимых интерфейса: `DiscountStrategy` (только скидки) и `CommissionStrategy` (только комиссии), чтобы классы не зависели от лишних методов.
5. **DIP (Инверсия зависимостей).** Сервис больше не зависит от конкретных цифр (0.05, 0.02) и строк. Он работает через абстракции (интерфейсы), а конкретные реализации подставляются через фабрики.

## Дополнительные улучшения

*   **Деньги:** Заменил `double` на `BigDecimal`. Для финансов `double` недопустим из-за ошибок округления.
*   **Типы:** Перевел строковые типы клиентов и оплаты в `enum`. Теперь нельзя сделать опечатку в названии.
*   **Магические числа:** Вынес проценты в константы, чтобы их можно было менять в одном месте.
*   **Логирование:** Заменил `System.out.println` на стандартный логгер (`Logger`), а для форматирования сумм в чеке использовал `DecimalFormat`.

## Проверка

Поведение системы осталось прежним: на тестовых данных (`VIP/CARD` на 1000 и `REGULAR/CASH` на 20) программа выдает те же результаты (970.00 и 20.00), что и оригинальный легаси-код.

## Миграция сборки с Maven на Gradle

В рамках третьего задания проект был переведен на систему сборки Gradle:

1. **Демонтирована конфигурация Maven:** удален `pom.xml`, а также файлы Maven Wrapper (`mvnw`, `mvnw.cmd`) и папка `.mvn`.
2. **Настроен `build.gradle`:** создан новый файл сборки с сохранением всех прежних настроек (Java 21, кодировка UTF-8). Сторонних зависимостей в проекте не было, поэтому миграция прошла без добавления новых библиотек.
3. **Обновлен `.gitignore`:** удалены правила, специфичные для Maven (`target/`), и добавлены правила для Gradle (`.gradle/`, `build/`).
4. **Написана кастомная Gradle-таска:** добавлена задача `generateBuildInfo`, которая автоматически генерирует файл `build/build-info.txt` с версией проекта и текущей датой сборки. Таска привязана к жизненному циклу `build`.

**Как проверить работоспособность:**
* Собрать проект: `./gradlew build` (или `.\gradlew.bat build` на Windows). После сборки в папке `build/` появится файл `build-info.txt`.
* Запустить приложение: `./gradlew run`.
